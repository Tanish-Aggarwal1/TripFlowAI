`TripSearchRepositoryImpl` (modified) — extract the shared match fragment and add the filters:
- Pull the text-match predicate into one private static final String constant used by BOTH the public and the owner queries (D-11), so the two differ only in scope plus the owner query's extra filter chain. It matches title, tags, and now place-names: `(:pattern IS NULL OR t.title ILIKE :pattern OR EXISTS (SELECT 1 FROM unnest(t.tags) tag WHERE tag ILIKE :pattern) OR EXISTS (SELECT 1 FROM stops s JOIN places p ON p.id = s.place_id WHERE s.trip_id = t.id AND p.name ILIKE :pattern))`. The place-name arm must be an `EXISTS` subquery, not a top-level join: a top-level join emits one row per matching stop, so a trip with three matching stops would appear three times and inflate the count. This is the same reason the tags arm already uses `EXISTS` over `unnest`.
- Append the filter chain to the owner query's WHERE, each clause null-tolerant so an unset filter is a no-op and all supplied filters AND together (D-12): `AND (CAST(:status AS text) IS NULL OR t.status = CAST(:status AS text))`, the same for `visibility`, `AND (CAST(:startDateFrom AS date) IS NULL OR t.start_date >= CAST(:startDateFrom AS date))` and the mirrored upper bound (D-13 — `start_date`, when the trip happens, deliberately not `created_at`), and `AND (CAST(:durationDays AS int) IS NULL OR (SELECT COALESCE(MAX(s.day_number), 0) FROM stops s WHERE s.trip_id = t.id) = CAST(:durationDays AS int))`. Bind enums as their `name()` strings so the native comparison matches the varchar column and the `V10` check constraint. If Postgres rejects an untyped bind in a null-comparison position, cast the parameter rather than branching the SQL string on which filters are present — a single static query text is what keeps this readable and injection-proof.
- The `COALESCE(..., 0)` implements the Discretion call left open by D-14: a zero-stop or never-optimized trip reports duration 0 rather than being silently dropped, consistent with D-07's zero-stops convention. Without it, `MAX(day_number)` over unscheduled stops yields SQL NULL, the equality silently evaluates false, and every never-optimized trip vanishes from a duration-filtered list with no error.
- `durationDays` stays a filter input only; it is deliberately not added to the response DTO. Nothing in this phase's decisions asks for a duration badge, and exposing it would put an extra correlated subquery on every trip-list read for a field no screen renders.
- Apply the identical predicate set to the count query — a count that disagrees with the id query produces a page whose `totalElements` lies.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser -> `GET /api/trips?search=…&status=…` | Free-text and typed filter values from an untrusted client reach query construction here. |
| repository -> Postgres (native SQL) | The only place in this phase where request-derived text meets SQL. |
| requester <-> other users' trips | The owner-scope predicate is the whole boundary; a leak here is a cross-account disclosure. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-09 | Tampering | `TripSearchRepositoryImpl.searchOwnedTrips` native queries | high | mitigate | Query text is a static string constant; every user-derived value (pattern, userId, status, visibility, both dates, durationDays, limit, offset) enters via `.setParameter(...)`, matching the existing `searchPublicTrips` implementation exactly. Acceptance criteria assert a bind count and a zero-count on concatenation into query text. |
| T-02-10 | Information Disclosure | `searchOwnedTrips` owner scoping | high | mitigate | `t.user_id = :userId` sits in the WHERE clause of BOTH the id query and the count query, sourced from `principal.userId()` and never from a request parameter — so another user's trip can neither be returned nor counted, which would leak its existence through `totalElements`. A `TripSearchRepositoryIT` case asserts a matching PUBLIC trip owned by someone else returns 0 results. |
| T-02-11 | Information Disclosure | D-08 boundary under search | high | mitigate | `searchOwnedTrips` re-fetches into `TripOwnerSummaryResponse`; `searchPublicTrips` keeps `TripSummaryResponse` untouched. Extracting the shared match fragment must not extract the projection — the two refetch queries stay separate. Plan 02-03's record-component guard test remains the tripwire. |
| T-02-12 | Denial of Service | filter/search query cost | medium | mitigate | The id query is `LIMIT`/`OFFSET`-bounded by `Pageable` before any refetch, and the endpoint is behind the existing default-deny `SecurityConfig`, so it is authenticated-only. The `ILIKE '%…%'` and per-row `MAX(day_number)` subquery are sequential-scan shaped; accepted at current scale, and the `TripSearchRepository` javadoc already records full-text search (tsvector + GIN) as the documented upgrade path if it stops being acceptable. |
| T-02-13 | Denial of Service / Input Validation | `TripController.listTrips` param binding | low | mitigate | `status`, `visibility`, both dates and `durationDays` bind to their real types, so Spring rejects an out-of-enum or malformed value at binding time into the canonical 400 `ApiError` path. Hand-parsing strings is explicitly rejected in the task action; a `TripControllerIT` case asserts the 400. |
</threat_model>
