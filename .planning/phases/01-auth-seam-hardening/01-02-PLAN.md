<objective>
Prove the whole refresh-token architecture end-to-end on one path before expanding it:
log in, receive an httpOnly refresh cookie, redeem that cookie once at
`POST /api/auth/refresh`, and get a fresh access token plus a rotated cookie back.

This is a **tracer**, not a prototype. Everything it lands is production-quality and
stays: the real Flyway migration, the real entity, the real hashing, the real cookie
attributes, the real CSRF gate. What it deliberately does NOT yet contain is the
revocation surface — reuse-detection and logout arrive in plan 01-03 and slot into the
service seams this plan establishes.

Purpose: the load-bearing risk in AUTH-04 is not the rotation algorithm, it is the
cross-site cookie topology (`RESEARCH.md` Pattern 3) and the ArchUnit constraint that
forbids the service layer from touching HTTP types. Both are proven or falsified by this
single slice, on the executor's freshest context.
Output: a working, committed, one-path refresh round-trip plus the cross-site delivery
configuration that makes it work in the deployed environment, not just in tests.
</objective>

<new_decision>
## D-07 (new, decided during planning — RESEARCH.md Open Question 1)

**Refresh-token lifetime: 30 days, fixed from issuance (not sliding.)**

`RESEARCH.md` flagged this as unspecified anywhere in CONTEXT.md, REQUIREMENTS.md or
`docs/`, and explicitly instructed the planner to decide rather than infer. 30 days
fixed is chosen because: (a) it is the common default for a consumer travel app where
re-login every month is unremarkable; (b) fixed-from-issuance means an attacker holding
a stolen-but-unused token cannot extend its life by refreshing, which sliding expiry
would allow; (c) rotation already re-issues on every refresh, so an active user's session
survives indefinitely anyway — the 30 days is really "how long may a user be away before
re-login", which is the correct thing to bound.

Exposed as `app.refresh-token.expiration-days` (env `REFRESH_TOKEN_EXPIRY_DAYS`) so it is
tunable without a redeploy, matching the `app.jwt.expiration-ms` precedent.

## D-01 override confirmation (cookie SameSite)

CONTEXT.md D-01 named `SameSite=Strict` or `Lax` "unless research surfaces a reason
otherwise". `RESEARCH.md` Pattern 3 surfaced exactly that reason: the deployed frontend
(`tripflowai-frontend.onrender.com`) and backend (`tripflowai.onrender.com`) are
different `onrender.com` subdomains, which are cross-*site* for cookie purposes, so
`Lax`/`Strict` would silently fail to attach the refresh cookie in production while
working fine locally. This plan therefore ships `SameSite=None; Secure` with the CSRF
risk carried by a non-simple-request header gate instead. This is the escape hatch D-01
itself authorizes, not a unilateral override.
</new_decision>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser -> `POST /api/auth/refresh` (cross-site) | The frontend origin is a different site from the API origin; an httpOnly cookie crosses this boundary automatically on any credentialed request the browser is willing to make |
| any web page on the internet -> `POST /api/auth/refresh` | The endpoint is `permitAll` and cookie-authenticated, so it is reachable by a cross-site attacker page unless a control forces a preflight |
| application -> `refresh_tokens` table | Long-lived session material at rest; readable by anything that can read a DB dump or backup |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-04 | Information Disclosure | refresh token readable by injected script | high | mitigate | Cookie is `HttpOnly`, so no JavaScript (including an XSS payload) can read it; the raw value is never placed in a JSON body, asserted by `login_refreshTokenValueIsNotInResponseBody` |
| T-01-05 | Information Disclosure | `refresh_tokens` rows in a DB dump | high | mitigate | Only the SHA-256 hex digest is persisted; a dump yields no presentable token. Asserted by `refreshTokensTable_storesOnlyTheHash` |
| T-01-06 | Tampering (CSRF) | cross-site forced call to `/api/auth/refresh` | high | mitigate | `SameSite` cannot carry this (cross-subdomain topology), so an `X-Requested-With` requirement is enforced as the first statement of the handler; a simple cross-site form/image cannot set it, forcing a CORS preflight that only an allow-listed origin survives. Asserted by `refresh_withoutCustomHeader_returns400BeforeAnyTokenLookup` |
| T-01-07 | Information Disclosure | cookie leaking to unrelated tenants on the shared PaaS suffix | high | mitigate | No `Domain` attribute is ever set, making the cookie host-only; asserted by a source gate that no domain attribute is applied, and by the `Set-Cookie` assertion in `login_setsHttpOnlyRefreshTokenCookie` |
| T-01-08 | Spoofing | replay of a stolen refresh token | high | mitigate | Single-use rotation lands here (`usedAt` stamped on redemption, replacement issued); the full reuse-detection response is completed in plan 01-03. Until then a replayed used token is rejected as invalid — a fail-closed intermediate state, never fail-open |
| T-01-09 | Elevation of Privilege | credentialed CORS opening the whole API to any origin | high | mitigate | `setAllowedOrigins` keeps an explicit, env-bound origin list; `setAllowedOriginPatterns` is source-gated to zero occurrences, and Spring fails bean creation on a wildcard paired with credentials, so the misconfiguration cannot reach production silently |
| T-01-10 | Denial of Service | unauthenticated flooding of `/api/auth/refresh` | medium | mitigate | Deferred by design to plan 01-03, where rate limiting is designed together with the reuse-detection mass-revoke it must protect (a rate-limited endpoint that force-logs-out a target user is itself the DoS vector). Tracked, not dropped |
| T-01-11 | Information Disclosure | token material reaching application logs | medium | mitigate | Service logs the user id only; no log statement in `RefreshTokenService` or `AuthController` takes the raw token or hash as a parameter, consistent with `docs/LOGGING_STANDARD.md` |
| T-01-12 | Tampering | supply chain via new packages | low | accept | No new npm/pip/cargo/Maven dependency is introduced — `ResponseCookie`, `SecureRandom`, `MessageDigest` and `HexFormat` are all already on the classpath (RESEARCH.md Package Legitimacy Audit records zero packages to audit) |
</threat_model>
