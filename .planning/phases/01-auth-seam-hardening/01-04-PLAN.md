<interface_context>
**Backend contract this plan consumes (shipped by plans 01-02 and 01-03 — read `01-03-SUMMARY.md`, which is authoritative over this summary):**

- `POST {apiBaseUrl}/auth/refresh` — no body. Requires the `refresh_token` cookie (sent automatically by the browser when the request is credentialed) AND an `X-Requested-With` request header, which is the CSRF control. Returns 200 `{ token, tokenType, expiresAt }`. Returns 400 without the header, 401 for a missing/expired/revoked/replayed cookie, 429 when rate limited. Sets a rotated `refresh_token` cookie.
- `POST {apiBaseUrl}/auth/logout` — no body, same cookie plus header requirement. Returns 204 unconditionally and clears the cookie.
- `POST {apiBaseUrl}/auth/login` and `/auth/register` — response body shape is UNCHANGED (`AuthResponse`); they now additionally set the refresh cookie.
- The cookie is `HttpOnly`, so JavaScript can never read it. Do not attempt to. The only thing the client controls is whether a request is credentialed.

**Existing frontend symbols (do not restructure):**

- `AuthService` (`core/services/auth.service.ts`) — `providedIn: 'root'`; private `baseUrl` = `${environment.apiBaseUrl}/auth`; `isAuthenticated` signal; `login`/`register` returning `Observable<AuthResponse>` and funnelling through private `handleAuthSuccess(res)` / `handleAuthError(err)`; `getToken()`; `hasValidToken()` (decodes the JWT payload and compares `exp`); module-level constants `TOKEN_KEY` and `USER_KEY`.
- `authInterceptor` — attaches `Authorization: Bearer` only when `req.url.startsWith(environment.apiBaseUrl)` AND the URL is not an `/api/auth/` path. **This exclusion is why the refresh and logout calls need no bearer token and why they will not accidentally receive one.**
- `sessionExpiryInterceptor` — currently calls `authService.logout()` on ANY 401 except login. This is the behavior D-06 replaces.
- `backendAvailabilityInterceptor`, and the registration order in `main.ts`: `[authInterceptor, sessionExpiryInterceptor, backendAvailabilityInterceptor]`.
- `ToastService` (`core/services/toast.service.ts`) — `showError(err, fallback, duration)` / `showSuccess(message, duration)`, wrapping Ionic's `ToastController`.
- `AuthResponse` (`core/models/auth.model.ts`) — `{ token, tokenType, userId, username, expiresAt }` where `expiresAt` is an ISO instant string.

**Project conventions that constrain this plan (`docs/frontend-standards.md`, CLAUDE.md):** standalone components only; `@if`/`@for` control flow, never the legacy structural directives; `inject()` for DI, never constructor injection (`@angular-eslint/prefer-inject` fails the build otherwise); specs co-located, using `provideHttpClient()` + `provideHttpClientTesting()`, plus `provideIonicAngular()` / `provideRouter([])` as the component under test needs.
</interface_context>

<simplification_note>
**No new HTTP interceptor is added, deliberately.** RESEARCH.md's recommended structure included a
`refresh-credentials.interceptor.ts` that would clone auth-cookie-bearing requests with
`withCredentials: true`. Exactly two requests in the entire application need credentials, and both
are issued from one place (`AuthService`), so setting the option directly on those two calls is
strictly smaller than a new interceptor plus its spec plus its registration plus the URL gating that
RESEARCH.md Pitfall 2 warns is easy to get wrong — a blanket credentials interceptor is precisely how
the Mapbox/Cloudinary requests would start failing preflight. Do not add the interceptor back; if a
third credentialed call site ever appears, that is the moment to reconsider.
</simplification_note>

    - A successful refresh that reports a new expiry re-arms the timer, so a second refresh fires after the next interval — proving the loop sustains rather than firing once.
    - An expiry already in the past schedules the refresh immediately rather than computing a negative delay and never firing.
    - A failed refresh moves `status` to the expired value and does NOT re-arm the timer, so a dead session does not spin.
    - Two consecutive schedule requests leave exactly one live timer — the old one is cleared, so a rapid re-login cannot produce duplicate refresh calls.
    - When the document becomes visible again after the scheduled point has passed, a refresh is attempted rather than the service trusting a timer that may not have fired while the tab was backgrounded.
  </behavior>
  <action>
    Create `SessionStateService` in `core/services/`, `providedIn: 'root'`, using `inject()` for
    `AuthService`. It exposes a readonly `status` signal with the three states active, refreshing and
    expired, and holds one private timer handle.

    Arm the timer from an `effect()` on `AuthService.expiresAt` rather than by having `AuthService` call
    into this service — the dependency must point one way only (this service knows `AuthService`;
    `AuthService` must never import this one), or Angular's injector will cycle. Compute the delay as
    the expiry instant minus now minus a one-minute buffer, clamped at zero so a stale or past expiry
    fires immediately instead of scheduling a negative timeout. Always clear any existing timer before
    setting a new one.

    Use a single self-rearming timeout, not a polling interval: an interval drifts and double-fires
    across laptop sleep/wake, and the re-arm falls out for free because a successful refresh updates
    `expiresAt`, which re-runs the effect. Because a backgrounded tab can have its timer throttled or
    fired late, also register a `visibilitychange` listener that, when the document becomes visible and
    the stored expiry is already within the buffer window (or past), triggers a refresh immediately.

    On the timer firing: set `status` to refreshing, subscribe to `AuthService.refresh()`, and on
    success set `status` back to active — the re-arm happens via the effect, so do not schedule
    manually in the success path as well or the timer will be armed twice. On error set `status` to the
    expired value and do nothing else: per D-06 this service must not perform routing, must not touch
    browser storage, and must not show any UI. Presentation is task 3's job.

    Finally, inject `SessionStateService` in `AppComponent` so the root-provided service is actually
    instantiated at bootstrap — a `providedIn: 'root'` service that nothing injects is never
    constructed and its effect never runs, which would make the whole timer dead code.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser JavaScript -> refresh cookie | The cookie is httpOnly; application code, and therefore any injected script, can influence only whether a request is credentialed, never read the value |
| SPA -> cross-site API origin | Every credentialed call crosses a site boundary and is subject to the backend's origin allowlist and preflight |
| expired-session UI -> user | The moment between "refresh failed" and "user notices" is a window where stale UI state is on screen |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-21 | Information Disclosure | injected script exfiltrating the refresh token | high | mitigate | No code path reads the cookie; the client only sets the credentialed request option. Source-gated by the absence of any cookie-reading API in the changed files, and structurally guaranteed by `HttpOnly` from plan 01-02 |
| T-01-22 | Information Disclosure | credentials attached to third-party requests (Mapbox, Cloudinary) | high | mitigate | The credentialed option is set on exactly two calls inside `AuthService`, never by a blanket interceptor — the failure mode RESEARCH.md Pitfall 2 describes is designed out rather than guarded against. Gated by the source assertion that no credentials interceptor exists |
| T-01-23 | Spoofing | stale session appearing usable after refresh failure | medium | mitigate | The status signal flips on the first refresh failure and any subsequent 401, and the first user interaction is intercepted with a blocking dialog; the user cannot keep operating a dead session unaware |
| T-01-24 | Repudiation | logout that never reaches the server | medium | mitigate | `logout()` posts to the server-side revocation endpoint before clearing local state, so the refresh token is dead server-side rather than merely forgotten client-side; local teardown still runs on failure so a user is never trapped |
| T-01-25 | Denial of Service | refresh loop hammering the endpoint after failure | medium | mitigate | A failed refresh sets the expired status and does NOT re-arm the timer, asserted by a spec case; combined with the backend rate limit from plan 01-03, a wedged client cannot flood the endpoint |
| T-01-26 | Tampering | CSRF header omitted, silently breaking the flow | low | mitigate | The header is set at both call sites and source-gated; the backend returns 400 without it, so an omission fails loudly at the first refresh rather than degrading quietly |
| T-01-27 | Tampering | supply chain via new packages | low | accept | No new npm dependency — signals, `setTimeout`, `visibilitychange`, `HttpClient` options and Ionic's `AlertController` are all already present |
</threat_model>
