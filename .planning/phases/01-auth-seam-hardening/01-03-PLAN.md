<task type="checkpoint:decision" gate="blocking">
  <name>Checkpoint: confirm the one-way reuse-detection revocation policy (D-03)</name>
  <decision>Lock the reuse-detection blast radius: on replay of an already-redeemed refresh token, revoke ALL of that user's refresh tokens (every device), per CONTEXT.md D-03.</decision>
  <context>
    D-03 is rated **one-way** in CONTEXT.md. Once shipped, this behavior becomes something users and
    any future client can depend on, and loosening it later to per-token or per-family revocation is a
    user-visible behavior change, not a refactor. The next task bakes it into `RefreshTokenService` and
    the `refresh_tokens` access pattern, so this is the last cheap moment to reconsider.

    Two consequences the developer should confirm they accept, both surfaced by RESEARCH.md:

    1. **Multi-tab false positives are expected, not a bug.** An httpOnly cookie is shared across all
       tabs of a browser profile. If tab A silently refreshes, tab B is still holding the old cookie
       value; when tab B's timer fires, its request is indistinguishable from a stolen-token replay
       and will trip the mass revoke — logging the user out everywhere. A cross-tab token-sync
       mechanism would fix this but is out of phase scope (CONTEXT.md never asked for it, and D-05/D-06
       do not mention multi-tab coordination). A QA report of "tab 1 logged out tab 2" is correct behavior.
    2. **Access tokens already issued keep working for up to 15 minutes after a mass revoke.** They are
       stateless JWTs with no denylist. RESEARCH.md Open Question 2 recommends accepting this because
       the D-02 lifetime is already short; the alternative is an access-token denylist, which is a
       materially larger piece of work not requested anywhere in this phase.
  </context>
  <options>
    <option id="option-a">
      <name>Ship D-03 as written — user-wide revoke on reuse detection</name>
      <pros>Matches the locked decision; strongest response to a real token-theft signal; simplest schema (no family/lineage columns needed, already reflected in the shipped V12); no further design work</pros>
      <cons>Multi-tab users can be logged out of every device by an entirely benign race; irreversible in the sense that relaxing it later changes observable behavior</cons>
    </option>
    <option id="option-b">
      <name>Narrow the blast radius to the replayed token only</name>
      <pros>No multi-tab false positives</pros>
      <cons>Contradicts the locked D-03 decision; a genuine attacker who stole a token keeps every other session they may also hold; would need a CONTEXT.md amendment before it could be planned</cons>
    </option>
    <option id="option-c">
      <name>Ship D-03 as written, and additionally log a distinguishable audit event on every mass revoke</name>
      <pros>Same policy as option A, plus operational visibility into how often the multi-tab false positive actually fires in real use, which is the data a future decision to narrow it would need</pros>
      <cons>Marginally more code; the log line must carry a user id only, never token material</cons>
    </option>
  </options>
  <resume-signal>Select: option-a, option-b, or option-c. Selecting option-b halts this plan — it requires a CONTEXT.md amendment before task 1 can proceed.</resume-signal>
</task>
