  <behavior>
    - Given a viewer whose interests include one tag value, and two PUBLIC trips — an older one carrying that tag and a newer one carrying a different tag — the older matching trip appears first.
    - Given two PUBLIC trips both carrying a matching tag, the more recently created appears first (recency is the within-group tiebreaker).
    - Given two PUBLIC trips carrying no matching tag, the more recently created appears first.
    - A viewer with an empty interests array receives a purely recency-ordered feed with a 200 and no error.
    - A PRIVATE trip carrying a matching tag does not appear at all — ranking never widens visibility.
    - Two viewers with different stored interests receive differently-ordered feeds over the same seeded trip set.
    - Ranking reads the viewer's stored interests row; a viewer's own trips' tags have no effect on their feed order.
  </behavior>
  <action>
    1. `TripRepository.java` — add `Page<Trip> findPublicRankedByInterests(@Param("interests") Collection<String> interests, Pageable pageable)` as a native `@Query` with an explicit `countQuery`. Filter to the PUBLIC visibility value. Order by a boolean match expression descending, then by the created-at column descending. Express the match as an `EXISTS` over `unnest` of the trip's tags column, testing membership of each unnested tag in the bound `:interests` collection.

       Deliberate deviation from 06-RESEARCH.md Pattern 4, which sketched the Postgres array-overlap operator: overlap requires binding a `text[]` parameter, which in practice means assembling a Postgres array literal string out of free-text, user-supplied interest values — a value containing a comma, brace or double quote silently corrupts that literal. The `unnest` plus `IN` form takes an ordinary collection parameter the JPA layer expands as bound values, so no literal is ever constructed and no escaping is required. The semantics are identical: both answer "do these two sets share at least one element."

       The created-at tiebreaker is not cosmetic. Without a total ordering, Postgres may return rows in a different order at offset 20 than it did at offset 0, which is precisely how a paginated feed starts duplicating and skipping trips.

    2. `TripService.listFeed` — before querying, load the viewer through `UserRepository` and read their stored interests. When the list is non-empty, call `findPublicRankedByInterests`; when it is empty, keep calling the existing `findByVisibility` recency finder. Branch explicitly rather than binding an empty collection: an empty `IN` list is a SQL syntax error, not a query that matches nothing. Leave the batched photo fetch and the mapper call from 06-01 untouched — this task changes which rows come back and in what order, nothing about how they are shaped.

    3. `DiscoveryFeedControllerIT.java` — add the seven behaviors above. Seed created-at values deliberately so the "older but matching outranks newer but not" case cannot pass by accident, and assert on the returned sequence of trip ids rather than on a single element.
  </action>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → `GET /api/discovery/feed` | Client-supplied paging and sort parameters cross into a query whose ordering is the feature |
| Viewer's stored interests → ranked SQL | Free-text, user-supplied values are bound into a native query |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-06-01 | Tampering (SQL injection) | Binding free-text interests into a native ranked query | high | mitigate | Interests are bound as a JPA collection parameter expanded into placeholders, never concatenated and never assembled into a Postgres array literal string. This is the stated reason Task 1 deviates from the array-overlap sketch: the overlap form requires literal construction from values a user controls, and the `unnest` plus `IN` form does not. |
| T-06-06-02 | Information Disclosure | Ranking widening visibility beyond PUBLIC | high | mitigate | The visibility filter lives in the query's `WHERE` clause and the ordering expression is confined to `ORDER BY`, so no reordering can surface a PRIVATE trip. Pinned by a dedicated integration test seeding a PRIVATE trip carrying a matching tag and asserting its absence. |
| T-06-06-03 | Tampering | Client sort parameter overriding the ranking | medium | mitigate | Task 2 rejects a non-default sort using the same mechanism `searchPublicTrips` already uses, so ranking cannot be silently disabled from the client, and a test pins the behavior. |
| T-06-06-04 | Information Disclosure | Docs advertising a public discovery surface after it was closed | medium | mitigate | Task 3 corrects `docs/api-contracts.md` and `docs/auth.md`, with a grep-backed acceptance criterion that no discovery path remains in the auth permitAll table. Stale docs are how a future contributor re-opens a closed finding. |
| T-06-06-05 | Denial of Service | Unbounded page size on the ranked query | low | mitigate | The feed handler's `@PageableDefault(size = 20)` bounds the page, and the ranked query carries an explicit `countQuery` so the count is a bounded aggregate rather than a materialized result set. |
| T-06-06-SC | Tampering | npm/maven installs | low | accept | No new package on either side — the ranked query uses Spring Data facilities already in use and this plan touches no frontend dependency. |
</threat_model>
