<objective>
Ship the minimal user profile of D-07: username, join date, and stored interests, backed by a new `User.interests` array column.

This is the phase's only schema addition to an existing core entity, and it is the data source D-06 explicitly chose for the feed ranking — interests come from what the user stored on their profile, not from an inference over their trip history. Plan 06-06 consumes the column; nothing here computes ranking.

**Schema pluralization note (advisory, `no-change`):** `User` gains richer profile shape for the first time beyond its auth fields. This is an additive field on the existing identity entity, not a second identity or tenant concept competing with the first — no promote/add-alongside decision is warranted.

Join date needs no new field: `User` extends `BaseEntity`, which already carries an audited `createdAt`.

Purpose: SOCIAL-05, and the D-06 data source that 06-06 depends on.
Output: `GET`/`PATCH /api/profile`, a `/profile` page, and a queryable `users.interests` column.
</objective>

  <decision>
    CONTEXT.md left the interest-tag taxonomy to discretion, requiring only that it be queryable for D-05's ranking match. Two shapes are viable and the choice is expensive to reverse once users have stored data.

    **Recommended option (A): free-text `TEXT[]` on `users`, mirroring `Trip.tags` exactly.** `Trip.tags` — the other half of the overlap match — is already unconstrained free text, so a fixed taxonomy on the interests side would only match trips whose free-text tags happened to use the same vocabulary, gaining typo-safety on one side of a comparison whose other side has none. It also keeps the ranking query to a single Postgres `&&` operator with no join.

    Option B: a fixed enum or lookup-table taxonomy. More correct long-term — canonical vocabulary, typo-proof matching, a pickable UI list — but it is new schema and new UX surface, and it does not fix the free-text tag side of the match.

    Consequences of option A, all intentional: matching is case-sensitive and typo-sensitive; a user typing "Hiking" does not match a trip tagged "hiking". If that proves too lossy in use, the cheap follow-up is normalizing both sides to lowercase at write time, not migrating to a taxonomy.

    Also confirm as part of this gate: field limits reuse `Trip.tags`'s already-documented policy (max 20 elements, each max 50 characters) rather than inventing new ones.
  </decision>
  <options>
    a) Free-text `TEXT[]` mirroring `Trip.tags`, limits 20 x 50 (recommended)
    b) Fixed taxonomy via enum or lookup table
  </options>

| T-06-05-SC | Tampering | npm/maven installs | low | accept | No new package on either side — the array column uses Hibernate facilities already in use by `Trip.tags`, and the page uses Ionic components already installed. |
