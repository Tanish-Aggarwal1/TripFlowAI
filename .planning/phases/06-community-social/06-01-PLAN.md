<objective>
Deliver the authenticated, feed-shaped backend that SOCIAL-01 actually needs, and the Angular data seam that consumes it.

Two things are wrong with the shipped discovery surface for this phase's purposes. First, `SecurityConfig` `permitAll()`s `/api/discovery/**`, which directly contradicts SOCIAL-01 ("Authenticated users can browse") and CONTEXT.md's Phase Boundary ("the feed requires authentication, it is not a public unauthenticated surface"). Second, the existing endpoints return `TripSummaryResponse`, a card projection with no stops, no owner and no tags — D-02's fixed header (trip name, location, owner username), D-02's fixed footer (description) and D-03's per-stop swipe content are all unrenderable from it.

This plan fixes both, end-to-end, on a real path: one PUBLIC trip travels from Postgres through a new `GET /api/discovery/feed` into an Angular `DiscoveryService` call, proven by an integration test and a service spec. Ranking (D-05/D-06) is deliberately NOT here — this plan orders by recency; plan 06-06 replaces the ordering clause once `User.interests` exists.

Scope framing per D-08: this is fall-break feature work, not winter hardening.

Purpose: SOCIAL-01's data contract, and the security correction it depends on.
Output: An authenticated `/api/discovery/feed` endpoint returning `FeedTripResponse`, plus the Angular service/model pair that calls it.
</objective>

  <decision>
    SOCIAL-01 and CONTEXT.md's Phase Boundary both require the discovery surface to be authenticated-only. The shipped `SecurityConfig` permits it anonymously, and `DiscoveryControllerIT` has passing tests asserting 200 with no `Authorization` header.

    **Recommended option (A): remove the whole `/api/discovery/**` entry from the permitAll matcher list.** CONTEXT.md's wording covers the whole discovery surface, not just the new `/feed` path; carving out only `/feed` leaves `GET /api/discovery/trips` and `GET /api/discovery/search` publicly enumerating every PUBLIC trip in the system, which is the same information-disclosure posture SOCIAL-01 was written to end.

    Option B: keep `/api/discovery/trips` and `/api/discovery/search` anonymous, add only `/api/discovery/feed` behind auth. Smaller blast radius on any existing consumer, but leaves the finding half-open and contradicts the Phase Boundary as written.

    Consequences of option A, all intentional: three existing `DiscoveryControllerIT` tests (`search_noAuth_missingQParam_returns400`, `search_noAuth_titleMatch_returnsPublicTripsOnly`, `listPublicTrips_noAuth_returnsOnlyPublicTrips`) change expected status, and RISK-R2 in the project risk register requires a real Postman/browser regression pass after any SecurityConfig change — a MockMvc assertion alone does not discharge it.
  </decision>
  <options>
    a) Remove `/api/discovery/**` from permitAll entirely (recommended)
    b) Carve out only `/api/discovery/feed` as authenticated, leave the other two anonymous
  </options>
  <default>a</default>
  <resume-signal>Reply "a" or "b" (or "approved" to take the recommended option a) to continue.</resume-signal>
  <done>The chosen option is recorded in the plan SUMMARY with a one-line rationale, and Task 2 implements that option.</done>
