<objective>
Deliver SOCIAL-07: trip-level 1-5 star ratings, one per user, on the join-table pattern the codebase already uses for likes.

Ratings differ from likes and saves in one structural way that drives the whole design: a like is a toggle (present or absent) while a rating is a *value* a user can change. That makes insert-if-absent wrong here — a naive second insert either violates the composite primary key or, worse, accumulates rows that silently skew the average. The mechanism is the same native `@Modifying` query the likes repository already uses; only the conflict action changes from do-nothing to do-update.

SOCIAL-07 was untracked in `REQUIREMENTS.md` until the phase research gap-check surfaced it on 2026-08-31; it has been referenced by the ROADMAP's 06-04 plan item and `docs/social-features-traceability-audit.md` since the fall plan's inception. The requirement now exists and this plan closes it.

**Placement note relative to D-04:** D-04 enumerates like, save and clone on the action rail. The star control is rendered in the same rail below clone. This is additive to D-04's set, not a substitution — no listed action is moved or removed, and the "never has to leave the feed" property D-04 exists to guarantee is extended to rating rather than weakened.

Purpose: SOCIAL-07.
Output: `trip_ratings` table, rate and rating-summary endpoints, and a star control on the feed card's action rail.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser → `/api/trips/{id}/rate` | An untrusted integer crosses into a persisted value that feeds a public aggregate |
| `TripRatingService` → Postgres | Concurrent same-user rating writes race on one composite key |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-04-01 | Tampering | Out-of-range or negative rating value | medium | mitigate | `RateTripRequest.rating` is `@NotNull` with minimum 1 and maximum 5, rejected as a 400 with `fieldErrors` before any write; the `trip_ratings` table's `CHECK (rating BETWEEN 1 AND 5)` constraint independently refuses any value that reaches the database by another path. Both layers are asserted separately in `TripRatingServiceIT`. |
| T-06-04-02 | Tampering | Ballot stuffing via repeated rating submissions | medium | mitigate | The composite primary key on `(user_id, trip_id)` makes one row per user per trip a structural invariant, and the `ON CONFLICT ... DO UPDATE` upsert replaces rather than appends. A user cannot inflate a trip's average by submitting repeatedly regardless of client behavior. |
| T-06-04-03 | Information Disclosure | Rating or reading the summary of a foreign PRIVATE trip | medium | mitigate | `loadVisibleTripLite` is the first statement of both `rateTrip` and `getSummary`, producing 404 rather than 403 — the read path is gated identically to the write path so the summary endpoint cannot be used as an existence oracle the write path refuses. |
| T-06-04-04 | Information Disclosure | Rating summary exposing who rated what | low | mitigate | `TripRatingSummaryResponse` carries only an aggregate, a count, and the caller's own value — never another user's rating or identity. |
| T-06-04-05 | Denial of Service | Per-card summary fetch on a fast-scrolling feed | low | accept | One request per card that becomes active, bounded by human swipe rate and by the browser's own connection limits. Accepted over a denormalized average column, which would be a permanent consistency liability for a bounded, measurable cost. A batched summary endpoint is the upgrade path if measurement ever justifies it. |
| T-06-04-SC | Tampering | npm/maven installs | low | accept | No new package on either side — ratings reuse Spring Data JPA and the star control uses `ionicons`, both already installed. |
</threat_model>
